- [x] 4.1 Create `EdgeViewer/Platform_Linux.cpp` implementing `Platform.h` via `dladdr` (module path), `std::filesystem::read_symlink` + `/proc/self/fd` (physical path resolution), `std::filesystem::temp_directory_path()` (temp path), manual `%VAR%`/`$VAR` env expand (use `std::getenv`), `std::filesystem::copy` + `std::filesystem::temp_directory_path()` + a counter (temp file generation). - [x] 4.2 Create `EdgeViewer/EdgeLister_Linux.cpp`: a `QWidget*`-hosted embed. `gs_Views` maps `HWND` (= `QWidget*`, the plugin's own `QWidget` container) to the `QtWebEngineBackend` shared_ptr. The `Register` step is a no-op. The `Create` step: build a `QWidget*` container parented to DC's parent (using `QVBoxLayout`), add the `QWebEngineView` as a layout child via `layout->addWidget(view)`, set focus proxy to the view, return the container as the plugin handle (`gs_Views` keyed by the container, mirroring `qtpdfview_qt`'s pattern so DC's `ResizeWindow(GetListerRect)` operates on the plugin's own widget). The `WM_COPYDATA` indirection is replaced with direct `Navigator::Open` calls (Task 1.4 confirmed DC's main-thread contract).
- [x] 4.3 Create `EdgeViewer/WebView/QtWebEngineBackend.{h,cpp}` (~200 LOC): the `IWebView` impl around `QWebEngineView` + `QWebEngineUrlSchemeHandler`. Implement:
   - `NavigateToString` → `QWebEngineView::setHtml(html, QUrl("ev://assets.example/loader.html"))` (after rewriting `http://` → `ev://` in the HTML; Decision 3 / Decision 9).
   - `Navigate` → `QWebEngineView::setUrl(QUrl(uri))` (rewriting `http://local.example`/`http://assets.example` to `ev://`; everything else passes through).
   - `ExecuteScript` → `page()->runJavaScript(js)`.
   - `AddScriptToExecuteOnDocumentCreated` → `page()->scripts().insert(QWebEngineScript(...))`.
   - `RegisterVirtualHost` → records a host → folder pair in a process-wide `std::map` consulted by the `QWebEngineUrlSchemeHandler::requestStarted` callback. The handler dispatches by `url.host()`: `assets.example` → assets folder, `local.example` → registered file root. Use Task 1's confirmed `ev://` scheme convention.

GLOB shared sources (`DllMain.cpp`, `Globals.cpp`, `Navigator.cpp`, `ProcessorInterface.cpp`, `Processors/*.cpp`), platform sources (`Platform_Linux.cpp`, `EdgeLister_Linux.cpp`, `WebView/QtWebEngineBackend.cpp`), and link against Qt6. Output `EdgeViewer.wlx64`. Export control via GNU ld version script (`CMakeLists.txt` writes `EdgeViewer.version`: `{ global: ListLoadW; ListLoadNextW; ...; local: *; };`) with the 12 WLX symbols declared `extern "C"` in `DllMain.cpp`. Do **not** use `-fvisibility=hidden` (empirically: hidden-visibility symbols are not exported by GNU ld even when named in the version script).
- [x] 4.5 Configure install rules in CMake so `EdgeViewer.wlx64` is laid out next to `assets/` and `edgeviewer.ini` directly in the plugin dir (no `Resources/` wrapper) — `assetsPath()` is `GetModulePath()/assets`, mirroring the Windows package layout (`BuildMakeSetup.bat` flattens `Resources\` contents beside the DLL).
- [x] 4.6 `WebView/WebViewFactory.cpp` is fully `#ifdef _WIN32`-guarded (the header too); the Linux branch constructs `QtWebEngineBackend` directly in `EdgeLister_Linux.cpp` and never enters this file.

> **Note on scheme**: The Spike (Section 1) found that `http` cannot be registered as a custom scheme on Qt Web Engine (Chromium reserves `http`/`https` for actual web traffic). The **FallbackA** custom scheme `ev://EdgeViewer` is used instead. `QtWebEngineBackend::NavigateToString` rewrites `http://` to `ev://` in the loader HTML before passing to `QWebEngineView::setHtml`. The loaders' templates keep their `http://` references — the rewrite is invisible to them. The implementation uses `ev` per Fallback A (same as the originally-specified WebKitGTK fallback).
